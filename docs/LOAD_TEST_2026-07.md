# EASWA 배포 서버 동시접속 부하 실측 (2026-07-14)

교사연수(10~15명 동시)에서 배포 서버가 측광→모델적합 흐름을 견디는지 실측한 결과.
**결론 요약: 10명까지는 전원 성공하지만 fit이 사실상 직렬 처리되어 대기시간이 인원수에 비례해 늘어나고(10명 시 fit 약 12분), 15명 동시에서는 인스턴스가 죽어 fit 성공 0/15. 서버는 약 1분 내 자동 재시작으로 회복.**

- +177초 / +197초: fit 요청 2건이 즉시 503

## 3. 로컬 대조 — 동시 10명 1회 (localhost:5895, LG gram 16GB)

| 시나리오 | 측광 성공 | 측광 중앙값 | 측광 최대 | fit 성공 | fit 중앙값 | fit 최대 | 1인 전체 소요(중앙값) |
|---|---|---|---|---|---|---|---|
| 동시 10명 (로컬) | 10/10 | 8.8 | 13.2 | 10/10 | 88.0 | 107.3 | 1분 55초 |

- 같은 10명 동시 조건에서 **로컬이 fit 기준 약 8배 빠름** (중앙값 88초 vs 702초). 전원 완료까지 로컬 3분 17초 vs 프로덕션 13분 18초.
- 로컬에서는 측광 레이트리밋(6회/분/IP)이 정상 발동해 429가 4회 발생 → 자동 재시도로 전원 성공 (재시도 대기 ~30–60초는 위 측광 소요시간에 미포함, 전체 소요에는 포함).

## 4. 병목 진단: 측광 < fit

- **측광은 병목이 아님.** 번들 컷아웃 + 메모리 캐시 덕에 단독 2.2초, 15명 동시에도 중앙값 74초로 성공(마지막 1명 503은 인스턴스 붕괴의 전조).
- **fit(emcee MCMC)이 지배적 병목.** 소요시간이 인원수에 거의 정비례: 1명 70초 → 5명 341초(×4.9) → 10명 702초(×10.0). 단일 워커 + Python GIL + 무료 인스턴스의 제한된 CPU에서 CPU-bound MCMC가 완전 직렬화됨. 즉 **서버 전체 처리량은 fit 약 1건/70초로 고정**이며, 시차를 두더라도 총 소요시간은 줄지 않고 개별 대기만 분산됨.
- **붕괴 지점은 12~15건 동시 fit.** 10건까지는 (느리지만) 살아남고, 15명 시나리오에서 동시 fit이 12건에 도달하자 인스턴스 사망. 512 MB 메모리 한도가 유력 원인.

## 5. 부수 발견 (개선 후보)

1. **프로덕션에서 측광 레이트리밋(6회/분/IP)이 작동하지 않음.** 로컬에서는 발동(429×4)했지만 Render에서는 15명 동시에도 0회. uvicorn이 `--proxy-headers` 없이 실행되어 `request.client.host`가 실제 사용자 IP가 아닌 Render 내부 프록시 IP로 잡히고, 프록시 IP가 연결마다 분산되어 버킷이 파편화된 것으로 추정. → 과부하 보호장치가 프로덕션에서 무력화된 상태. `X-Forwarded-For` 신뢰 설정 또는 전역(IP 무관) 동시 fit 상한 도입 검토.
2. **fit에는 레이트리밋 스코프 자체가 없음** (`transit_fit` 스코프가 `rate_limit_service._rate_limit_configs`에 미등록). 서버를 죽인 것이 바로 무제한 동시 fit이므로, 전역 동시 fit 세마포어(예: 2~3) + 초과 시 "대기 중" 응답이 가장 효과적인 방어.
3. 15명 규모에서도 **자동 재시작 회복은 약 1분**으로 빨랐고 데이터 손상 없음. 다만 붕괴 순간 진행 중이던 모든 사용자의 fit이 무통보 실패(스트림 절단)하므로, 수업 중 발생 시 혼란이 큼.

## 6. 연수 운영 권고

1. **동시 fit은 최대 5명, 권장 3명 이하로 통제할 것.** 5명 동시도 fit 대기 약 5.7분(전체 약 6분). 15명 일제 실행은 서버 다운을 유발하므로 금지. 12건 이상 동시 fit이 실측 붕괴 지점.
2. **시간차 실행 필수 — 3명 × 5개 조로 나눠 조별 순차(약 4분 간격)로 fit 실행.** 서버 처리량이 fit 1건/약 70초로 고정이므로 15명 전원 완료에는 어떤 방식이든 최소 약 18분 소요. 측광은 전원 동시에 시켜도 무방(15명 중앙값 74초).
3. **강사 노트북 로컬 서버를 백업으로 반드시 준비.** 동일 10명 부하를 로컬은 3분 17초에 전원 처리(프로덕션의 약 8배). 연수장 Wi-Fi에서 강사 PC IP로 접속시키는 플랜 B를 사전 리허설하고, Render가 죽어도 약 1분 내 자동 회복된다는 점을 진행 시나리오에 반영할 것.

## 7. 재현 방법·원자료

- 부하 스크립트/원자료(JSON)는 세션 스크래치패드(`load_test.py`, `prod_results.json`, `local_results.json`, `prod_recovery.json`)에 생성됨 — 세션 종료 시 소멸되므로 장기 보존 필요하면 레포로 복사할 것.
- 스크립트 개요: 워밍업(`/api/health` 200 확인) → `/api/targets/wasp_6_b` + `/observations` + preview로 실제 앱과 동일한 요청 컨텍스트 구성 → 시나리오 실행(가상 사용자별 측광 스트림 → 기본 BJD 창 재현 → fit 스트림) → 시나리오별 성공/실패·소요시간·오류 유형·health 기록. 429 수신 시 Retry-After 기반 자동 재시도(최대 5회).
