### 4. 개선1 — 용어·영어·기호·단위·그래프 기본 표기

식현상, KMTNet 미시중력렌즈, 성단 색등급도 세 모듈을 **현재 구현 순서와 실제 화면 순서**로 전수 확인한다. 코드 문자열 검색으로 끝내지 말고 렌더링된 화면에서 용어가 처음 등장하는 지점, 그래프 축, 단위, 범례, 도움말을 본다.

반드시 확인할 항목은 다음과 같다.

- 교사 응답이 직접 지목한 `BTJD`, `BJD`, `Rp/R*`, `χ²_red`, `ROI`
- 비교성 품질 그래프, 광도곡선, 잔차와 위상 그래프의 가로축·세로축 이름과 단위
- KMTNet의 실제 화면에 노출되는 `u₀`, `tE`, `χ²/dof`, 관측소·시간·밝기 관련 축과 단위
- 성단 색등급도에서 실제 사용하는 색지수, 등급, 축 방향, 전향점 등 학습자가 판단에 써야 하는 표기
- 한국어 화면에 불필요하게 남은 영어와 영어 화면의 과학적 의미 불일치

처리 원칙은 다음과 같다.

1. 짧은 한글 풀이를 **값이나 그래프가 실제로 나타나는 지점 가까이** 둔다. Step 0의 용어 목록에만 있으면 충분하지 않다.
2. 그래프 축에는 변수명과 단위를 함께 표시한다. 단위가 없거나 무차원인 경우 거짓 단위를 만들지 말고 필요한 경우 무차원임을 짧게 밝힌다.
3. 전체 이론 강의를 화면에 추가하지 않는다. 짧은 라벨, 한 줄 풀이, 기존 펼침 설명이나 툴팁을 우선 사용한다.
4. 설명은 학습자가 무엇을 보고 판단해야 하는지 알려 주되 결과의 원인과 정답을 먼저 확정하지 않는다.
5. KMTNet 자료를 합성 자료로 오인해 표기하거나 실제 자료의 출처·성격을 바꾸지 않는다. 실제 데이터와 표시 의미를 코드·자료 경로에서 확인한다.

완료 기준은 세 모듈별로 `용어/기호`, `축`, `단위`, `범례`, `표시 위치`, `한국어/영어`를 확인한 표가 남고, 교사 응답이 지목한 용어가 실제 등장 지점에서 이해 가능한지 화면으로 확인된 상태다.

### 5. 개선2 — 눈에 띄는 어색한 안내 문장과 문맥

세 모듈의 단계 안내, 버튼, 오류·대기 상태, 생각해보기, 해설, 결과 기록 화면을 실제 흐름대로 읽는다. 다음에 해당하는 문장만 우선 고친다.

- 문장 호응이 어긋나거나 목적어·주어가 빠져 뜻을 다시 읽어야 하는 문장
- `이것`, `위 값`, `해당 결과`처럼 가리키는 대상이 불명확한 지시어
- 현재 버튼·선택지·그래프와 맞지 않는 도움말
- 번역투, 불필요한 괄호·나열, 지나치게 기계적으로 이어지는 설명
- 화면이 실제로 하지 않은 동작을 했다고 쓰거나, 학습자가 선택해야 할 것을 플랫폼이 했다고 쓰는 문장

특히 식현상 Step 2·3의 O/X 생각해보기 아래에 **“모르면 `모르겠다`를 입력하라”는 취지의 도움말이 남아 있는지 확인한다.** O/X에는 입력칸과 `모르겠다` 선택지가 없으므로 이 문구가 실제로 남아 있으면 새 선택지를 추가하여 응답 구조를 바꾸지 말고, 다음과 같이 현재 생각을 선택하도록 안내 문장을 맞춘다.

> 확신이 없어도 지금 생각에 더 가까운 쪽을 고른 뒤 해설을 확인하세요.

자유서술 입력에서는 `모르겠다`도 유효한 학습자 응답으로 저장되어야 한다. 문체 교정의 목적을 AI 사용 은폐나 AI 탐지 회피로 쓰지 말고, **학습자가 안내와 다음 행동을 정확히 이해하게 하는 문장 정비**로 기록한다. 수정한 문장은 검증표에 `화면 위치 / 변경 전 / 변경 후 / 수정 이유`를 남긴다.

### 6. 개선3 — 단계 안내·도움 질문·이해 점검의 발견성

각 모듈에서 초보 학습자가 다음 세 가지를 바로 알 수 있는지 확인한다.

1. 이 단계에서 해야 할 일
2. 완료하기 위해 무엇을 선택·입력해야 하는지
3. 자신의 판단을 남긴 뒤 어디에서 해설을 확인하고 다음 단계로 가는지

구현 원칙은 다음과 같다.

- 기존 단계 카드와 `생각해보기` 컴포넌트를 우선 사용한다. 갑자기 뜨는 퀴즈 팝업을 새로 만들지 않는다.
- 한 화면에 같은 개념을 묻는 생각해보기가 중복되어 있지 않은지 확인한다. 최근 커밋에서 질문이 이동·추가됐으므로 특히 성단과 KMTNet을 다시 본다.
- 질문은 답의 근거가 되는 자료·그래프·처리가 화면에 나타난 뒤 배치한다. 아직 보지 않은 정보를 묻지 않는다.
- 학습 증거로 사용하는 생각해보기는 응답 전에는 다음 단계 완료 조건을 충족하지 않아야 한다. 다만 정답을 강요하지 말고 자유서술의 `모르겠다`도 응답으로 인정한다.
- 폐쇄형 문항은 첫 선택을 기록한 뒤 바꿀 수 없게 하고, 해설은 첫 응답 뒤에 보여 준다. 이미 구현된 잠금 로직을 중복하거나 서로 다른 상태 저장 방식을 새로 만들지 않는다.
- 단계 상단의 할 일, 실제 입력·선택 컨트롤, 생각해보기, 다음 버튼이 시각적으로 한 흐름으로 읽혀야 한다. 색이나 장식만 늘리지 말고 제목·간격·배치·상태 문구를 사용한다.
- 질문을 찾을 수 있는지, 질문에 답할 수 있는지, 응답이 실제 저장되는지는 서로 다른 검증 항목으로 확인한다.

### 7. 이번 작업에서 하지 않을 것

- 차시별 교수·학습안, 학생 활동지, 교사용 자료의 본격 개발
- LLM·MCP 챗봇이나 교사 대체 기능 추가
- 동시 접속 서버 구조 개편

- 과학 계산식, API 자료원, 분석 파라미터 또는 제출 스키마를 문장 개선에 끼워 바꾸기
- 실제 자료를 합성 자료로 교체하거나, 검증하지 않은 산출값을 교육용이라는 이유로 고정하기

전체 lint에 기존 오류가 있으면 성공으로 꾸미지 말고, 기존 오류와 이번 변경 파일의 오류를 분리한다. 변경 파일에는 새 TypeScript·ESLint 오류가 없어야 한다.

3. 데스크톱 1440px 폭에서 세 모듈의 변경 화면을 확인한다. 가능하면 390px 안팎의 좁은 폭에서도 축·도움말·버튼이 잘리거나 겹치지 않는지 확인한다.
4. 식현상은 권장 대상 `WASP-6 b`로 Step 1부터 최종 기록·제출까지 실제 한 번 수행한다. 용어·축·생각해보기·응답 잠금·새로고침 또는 초안 복원·제출 결과를 확인한다.
5. KMTNet과 성단은 최근 추가된 생각해보기의 자료 근거, 중복 여부, 완료 차단, 첫 응답 기록, 다음 단계 진입을 실제 수행한다.
6. 화면에서 본 결과와 코드·테스트 결과를 검증표에 적는다. 문자열 검색이나 빌드 성공만으로 UI 확인을 대신하지 않는다.

### 9. 커밋·배포·두 회차 고정

1. 다른 세션 변경과 섞이지 않게 이번 작업 파일만 선택적으로 스테이징한다.
2. 로컬 검증과 화면 검증이 끝난 뒤 커밋한다. 예시 제목은 `improve: finish preservice demo language and guidance audit`이다.
3. 첫 회차 전에 `main`으로 푸시하여 Render 자동배포를 완료한다. 푸시 직전 원격 `main`의 새 커밋을 확인하고 강제 푸시하지 않는다.
4. 라이브 `https://easwa-webapp.onrender.com/`에서 정적 자산 이름이 바뀌었는지, 변경 화면이 실제로 보이는지 확인한다. 로컬 빌드만 보고 배포 완료라고 쓰지 않는다.
5. 실제 배포 커밋 전체 해시, 커밋 시각, 라이브 JS/CSS 자산, 확인 시각을 `docs/DEMO_VERSION_RECORD.md`의 예비교사 조사 절에 기록한다. 현재 문서의 오래된 `[푸쉬 여부 확인 필요]`, 옛 자산 해시, 잘못 남은 예정일도 실제 2026-09-06·09-07 일정과 맞춘다.
6. **첫 회차가 시작된 뒤부터 둘째 회차가 끝날 때까지 `main`에 추가 푸시하지 않는다.** 치명적 장애 때문에 바꿔야 한다면 두 회차가 서로 다른 빌드를 보게 되므로 변경 시각·커밋·영향받은 참가자를 회차별로 기록한다.
7. 시연 시작 10분 전 사이트를 한 번 열어 Render의 첫 접속 대기를 해소한다. 상시 keep-alive는 설정하지 않는다.

### 10. 문서와 원고 기록

- `docs/시연전_개선1-3_검증기록_2026-09-06.md`: 화면별 판정, 변경 전후, 검증 근거
- `docs/DEMO_VERSION_RECORD.md`: 실제 배포 커밋·자산·회차

원고 v14 §4.6.2는 이미 확인된 전문 용어, 기준값 비교, 자가점검 잠금, 개념 확인 시점 조정을 기록하고 있다. 이번 작업으로 문장 교정이나 단계·질문 발견성의 실제 반영이 새로 확인됐을 때만 백업을 만든 뒤 그 범위만 추가한다. 설문 결과, 응답자 수, 교사 원문, 개선 선정 근거를 바꾸지 않는다. 구현을 선택했다는 사실과 라이브 배포 완료를 구분한다. 원고를 수정했다면 기존 구조·원자료 검증기를 다시 실행한다.

### 11. 완료 보고에 반드시 포함할 것

최종 답변은 다음 순서로 보고한다.

1. 개선1·2·3 각각 `이미 충족 / 이번 수정 / 남은 항목`
2. 수정 파일과 화면별 변경 전후

## 이 프롬프트가 고정하는 핵심 판단

- 시연 전 범위는 개선1~3이다.
- 개선1~3도 전부 새 기능을 만드는 것이 아니라 현재 화면을 먼저 검증하고 부족한 부분만 고친다.
- 문체 지적은 1명의 직접 응답에 근거한 제한된 교정이며, 전체 AI 탐지·은폐 작업이 아니다.
- 팝업과 LLM/MCP는 이번 구현 결정이 아니다.
- 개선4~9는 버리지 않고 향후 과제로 보존한다.
- 설문은 이미 확정됐으므로 앱 개선 세션에서 수정하지 않는다.
- 두 예비교사 회차 사이에는 배포본을 바꾸지 않는다.
