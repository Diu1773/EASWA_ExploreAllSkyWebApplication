# Learner UX Review (학습자 페르소나 UX 리뷰)

EASWA는 코딩 없이 실제 천문 데이터를 탐구하는 **교육용** 플랫폼이다. 따라서 화면의 성패는
"개발자/전문가가 보기에 멀쩡한가"가 아니라 **"실제 학습자가 시각적·인지적으로 어떻게 받아들이는가"**로 판단해야 한다.
이 스킬은 평가자가 세 페르소나에 **빙의**해 화면을 1인칭으로 써보고, 막히는 지점을 근거(스크린샷)와 함께 잡아낸다.

## 언제 쓰나
- 새 화면/플로우를 만든 직후 수용성 점검
- "이 단계가 헷갈리나? 없애야 하나?" 같은 IA 의사결정 전 검증
- 입문/심화 분기, 단계 흐름(Step), 버튼·문구·정보량 결정의 트레이드오프 판단

## 평가 페르소나 (셋 모두로 각각 리뷰)

**① 초보 학습자 (입문 시민/처음 접하는 학생)**
- 천문 배경 거의 없음. `광도곡선`·`차등측광`·`RUWE`·`ROI`·`flux` 같은 용어에서 막힘.
- 화면을 연 뒤 **3초 안에 "지금 뭘 하면 되는지"**가 안 보이면 이탈.
- 긴 문단·표는 안 읽음. 큰 버튼·시각물·**한 화면 한 행동**에 의존.
- 한 화면에 결정이 2개 이상이거나, 단계 위치("어디쯤이고 다음은 뭐")가 불분명하면 혼란.
- 체크: 첫 시선 유도가 1개인가? 용어에 설명/툴팁이 있나? 다음 버튼이 명확한가?

**② 중급 학습자 (개념은 아는 자기주도 탐구자)**
- 기본 개념 보유. **효율**을 원함 — 중복·불필요한 단계, 빈 클릭에 즉시 짜증.
- 자동화가 **블랙박스면 불신** — 자료 출처·분석 조건·모델 가정이 보이길 원함(원리 3).
- 바로 데이터로 뛰어들거나 **심화/지름길 경로**를 찾으려 함.
- 체크: 군더더기 단계가 없나? 자동 처리의 근거가 노출되나? 심화 진입로가 있나?

**③ 중·고등학생 (수업 맥락, 45–90분)**
- 동기·집중 편차 큼. **구조와 목표가 분명해야** 따라옴. "왜 이걸 하지"가 안 보이면 흥미 상실.
- 읽기 부담·시각적 잡음에 약함 → 산만해짐. 정보 과밀 화면에서 길을 잃음.
- 기록/해석 입력칸이 막연하면 **빈칸으로 둠**(원리 4 붕괴).
- 체크: 단계 목표가 한 줄로 분명한가? 한 화면 정보량이 과한가? 해석 질문이 답할 만큼 구체적인가?

## 평가 렌즈 = 5개 설계원리 + UX 휴리스틱
모든 발견은 아래 중 하나 이상에 매핑한다.
1. **탐구 주제 중심** — 천체명·표·좌표가 아니라 질문/현상에서 출발하는가?
2. **기술 실행 부담 완화** — 학습목표와 무관한 절차(검색·다운로드·반복클릭)를 강요하지 않는가?
3. **분석 과정 가시화** — 출처·관측정보·비교성 품질·분석조건·모델가정이 보이되, *과밀*하지 않은가? (블랙박스 금지 ↔ 정보 폭격 금지의 균형)
4. **결과 해석은 학습자** — 산출값만 던지지 않고, 비교·해석 질문이 답할 만한가?
5. **수업 적용** — 단계 흐름이 안내형인가? 입문/심화 분기가 있는가? 교사·학생이 시간 내 소화 가능한가?
+ 일반 휴리스틱: 시각적 위계, 인지 부하, 다음 행동의 명확성, 일관성(색·버튼 톤), 용어 친절도, 읽기 부담, 네비게이션 혼란.

## 절차
1. **대상 확정** — 인자로 받은 화면/플로우. 없으면 사용자에게 어떤 플로우인지 묻거나 핵심 플로우(예: 외계행성 블럭 Step0→6)를 대상으로 한다.
2. **시각 캡처** — 반드시 스크린샷 기반으로 평가한다(상상 금지).
   - `cd frontend && npm run build` → **프로덕션 서버(포트 5895)** serverId로 `preview_screenshot`. **dev 서버(5173)는 HMR 소켓 때문에 캡처가 멈추니 쓰지 말 것.** (`preview_list`로 serverId 확인. 메모리 `preview_screenshot_prod_server` 참조.)
   - 스텝 이동: `preview_click`으로 스텝퍼 원형(`button[title="<스텝 제목>"]`) 클릭. 화면 전환은 `preview_eval`의 `window.location.assign('/경로')`. **리로드/네비 직후 첫 캡처는 검게 나오니 한 번 더 캡처.**
   - 구조 확인은 `preview_inspect`/`preview_snapshot`도 병행(dev에서도 동작).
3. **페르소나별 1인칭 워크스루** — 각 페르소나로 화면을 "써보며" 서술: 0–3초 첫인상(시선이 어디로), 다음에 뭘 클릭할지, 어디서 멈칫/혼란, 안 읽고 건너뛸 텍스트, 막히는 용어, 비어둘 입력칸.
4. **발견 정리** — 각 이슈에 `심각도(차단/주요/경미) × 영향 페르소나 × 위반 원리 × 구체 수정안`.
5. **통합·우선순위** — 페르소나 공통으로 걸리는 이슈를 상단에. "한 줄 요약 + 무엇부터 고칠지".

## 출력 형식
```
## 대상: <화면/플로우>
### 초보 학습자 — 워크스루
<1인칭 서술 + 멈칫 지점>
### 중급 학습자 — 워크스루
### 중·고등학생 — 워크스루

## 발견 (우선순위)
| # | 이슈 | 페르소나 | 원리 | 심각도 | 수정안 |
|---|------|----------|------|--------|--------|
...
## 한 줄 결론 + 먼저 고칠 3가지
```

## 주의
- **리뷰만 한다. 코드 수정은 사용자 승인 후.** 발견과 수정안을 제시하되 임의로 적용하지 않는다.
- **사용자가 손수 만든 자산(Transit Lab `LabView`/`TransitLab`, `Transit3DScene`, `/tess`)은 평가 대상이되 함부로 고치지 않는다.** 칭찬할 건 칭찬한다(좋은 패턴은 다른 화면의 기준점으로 인용).
- 발견은 반드시 **캡처에 보이는 근거**에 기반한다. "그럴 것 같다"는 금지.
- 페르소나는 연기하되, 결론은 5원리라는 학술 근거로 정당화한다(논문 일관성).
